# Как мы работали с Claude

## Инструменты

| Что | Зачем |
|---|---|
| **Claude Code** — ИИ-ассистент Anthropic, расширение для VS Code (Windows) | Читает и пишет файлы проекта, запускает команды и тесты, делает скриншоты, работает с git |
| Python 3 | Эталонная реализация движка и тесты |
| Google Chrome в режиме без окна | Автоматические проверки страницы и скриншоты |
| git + GitHub + GitHub Pages | История версий, публикация кода, живое демо |

Claude работает прямо в папке проекта на моём компьютере. Он не только советует, а сам меняет файлы и запускает
проверки. Каждое действие видно в окне чата, опасные действия (например, публикацию) он делает только по моей команде.

## Порядок работы

Каждая задача проходила один и тот же цикл:

1. **Запрос.** Я описываю, что нужно, своими словами: цель, для кого, что не нравится.
2. **Уточнение.** Если решение за мной, Claude задаёт вопросы с вариантами ответа и своей рекомендацией
   («всё в браузере или нужен сервер?», «где хранить описание работы?»). Технические мелочи он решает сам.
3. **План.** Для больших задач — план по этапам. Я его утверждаю.
4. **Работа.** Claude пишет код и сразу тесты к нему.
5. **Проверка.** Автотесты + скриншоты страницы на компьютере и на телефоне. Claude сам смотрит на скриншоты
   и исправляет то, что выглядит плохо.
6. **Отчёт.** Коротко и простыми словами: что сделано, какие проверки прошли, что осталось.
7. **Моя проверка.** Я открываю приложение и смотрю как пользователь. Если непонятно или неудобно — новый запрос.
8. **Сохранение.** Коммит в git на моём компьютере. На GitHub — только когда я говорю «отправляй».
9. **Журнал.** В конце каждой сессии Claude дописывает журнал работы (из него сделана [хронология](2_хронология.md)).

После каждого этапа плана Claude готовил разбор: что сделано, как это работает простыми словами на числах проекта,
и вопросы для самопроверки — чтобы я понимал проект, а не только получил код.

## Правила, которые действовали

Правила записаны в файл `CLAUDE.md`, Claude читает его в начале каждой сессии
(подробно — [5_инструкции_для_claude.md](5_инструкции_для_claude.md)).

- Общение на русском, объяснения — простыми словами на числах проекта.
- Решения о том, каким быть приложению, принимаю я. Claude предлагает варианты и говорит, какой советует.
- Ничего не считается готовым без проверки: тесты должны пройти, страница — выглядеть нормально на скриншоте.
  Если тест не прошёл, Claude так и пишет.
- Любое изменение правил расчёта делается сразу в двух реализациях движка (JavaScript и Python),
  и они должны совпасть до последнего знака.
- На GitHub отправляется только по команде «отправляй». Личные файлы (переписка, заметки, разборы) не публикуются.
- Журнал работы дописывается каждую сессию, копия переписки хранится вместе с проектом.

## Как мы проверяли, что ИИ не ошибся

ИИ может ошибиться так же, как человек, поэтому каждое число проверялось независимо:

| Проверка | Что ловит |
|---|---|
| **Две реализации движка.** Python-эталон и JavaScript используют один генератор случайных чисел и при одном сиде должны выдать одинаковые числа до последнего знака | Ошибку в одной из реализаций |
| **Точные ответы.** Там, где ответ можно посчитать формулой или перебором (кубики, совещание из задания), Монте-Карло должен попасть в свою погрешность | Ошибку в самой математике |
| **Тест страницы «как пользователь».** Скрипт открывает приложение, нажимает кнопки, вписывает числа и сверяет ответ | Ошибки интерфейса: не та цифра, не та подпись, сломанная кнопка |
| **Скриншоты.** Компьютер, телефон, тёмная тема | То, что тесты не видят: обрезанный текст, кривая вёрстка |
| **Моя проверка как пользователя** | Непонятное и неудобное — то, что формально работает, но человеку не подходит |

Пример, когда это сработало: на первом этапе тест показал 0,60 вместо ожидаемых 0,54. Ошибка была в ожидании
теста, а не в программе: задержка ровно 5 минут — это ещё «вовремя». Тест исправили, программа была права.

## Как лучше формулировать запросы — что мы поняли

1. **Начинать с цели и пользователя, а не с решения.** «Это должно быть понятно обычному человеку» дало больше,
   чем «добавь кнопку».
2. **Показывать на конкретном примере, что не так.** «Я хочу спросить, найду ли работу до Нового года, —
   и не понимаю, куда это вписать» сразу показало проблему.
3. **Одна задача — один запрос.** Большие задачи — по этапам с проверкой после каждого.
4. **Давать ИИ задавать вопросы.** Многое, что казалось очевидным, имело несколько вариантов (сервер или браузер,
   ветка или папка).
5. **Возвращаться к заданию.** Самое важное решение проекта — остановиться и спросить: «а для чего приложение?».
   Попытки угадывать тему вопроса ломались на новых ситуациях. Вернулись к формулировке преподавателя —
   «по заданным распределениям» — и сделали универсальный конструктор.
6. **Явно говорить о публикации.** Всё, что уходит в интернет, — только по прямой команде.

Готовые формулировки всех запросов — в [3_запросы_и_промпты.md](3_запросы_и_промпты.md).
