# Инструкции для Claude (файл CLAUDE.md)

## Что это

`CLAUDE.md` — файл в папке проекта, который Claude Code читает в начале каждой сессии. Это «память проекта»:
о чём проект, какие решения приняты, как устроен код, какие правила соблюдать. Без него каждую новую сессию
пришлось бы объяснять всё заново.

Файл вёл сам Claude: после каждого шага он дописывал, что изменилось. В основной ветке файл не публикуется
(там рабочие заметки), а здесь — его аккуратная текущая версия.

---

## Текущая версия (сокращённо)

### О проекте
Учебный проект: веб-приложение, которое считает вероятности случайных событий по заданным распределениям методом
Монте-Карло. Движок взят из прошлого проекта автора — слота Snow Boom. Пример из задания: опоздание транспорта +
задержка обеда + занятая переговорка → начнётся ли совещание вовремя.

Автор не пишет код: код пишет Claude. Общение на русском, простыми словами. Решения о том, каким быть приложению,
принимает автор; Claude предлагает варианты с рекомендацией.

### Как устроено приложение
- Всё работает в браузере, без сервера; открывается двойным щелчком по `index.html`.
- `engine/engine.js` — движок: генератор с сидом, распределения, язык формул, прогон, статистика, точный перебор, связи.
- `app/simple.js` — интерфейс-конструктор: факторы → блоки расчёта → условие успеха; ответ словами; отчёт для PDF.
- `app/csv.js` — чтение CSV из русского Excel для фактора «по данным».
- `app/charts.js` — графики (SVG, без библиотек).
- `vendor/` — jsPDF и html2canvas, только для скачивания отчёта в PDF.
- `reference/` — Python-эталон движка, совпадающий с JavaScript до последнего знака.
- `tests/` — самопроверка движка и проверка страницы «как пользователь» в Chrome без окна.

### Правила
1. Любое изменение правил расчёта — в **обеих** реализациях (`engine.js` и `engine_ref.py`), затем обновить
   эталонные ответы; самопроверка должна пройти.
2. Ничего не объявлять готовым без проверки: тесты + скриншоты (компьютер и телефон). Если тест не прошёл — так и сказать.
3. После каждого этапа — разбор простыми словами на числах проекта и вопросы для самопроверки.
4. Дописывать журнал работы в конце каждой сессии и сохранять копию переписки вместе с проектом.
5. Коммиты — в git на компьютере автора. На GitHub — только по команде «отправляй».
6. Не публиковать личное: переписку, рабочие заметки, разборы. Не передавать личные данные во внешние сервисы.

### Команды проверки
```
cd reference; python -m unittest tests_ref      # Python-эталон: 54 теста
python reference/make_vectors.py                # эталонные ответы для сверки
python tests/run_selftest.py                    # движок в браузере: 58 проверок
python tests/run_selftest.py uitest             # страница «как пользователь»: 54 проверки
```

### Примеры для быстрой проверки

## Почему это работает

- **Контекст не теряется.** Новая сессия начинается с того, на чём остановились, с теми же правилами.
- **Правила проверяемы.** «Две реализации должны совпасть» и «тесты должны пройти» — это не пожелания,
  а условия, которые видно в выводе тестов.
- **Контроль у автора.** Всё, что уходит в интернет или меняет смысл приложения, решает человек.
